# V0.6 GPU Validation

This document records evidence from a real CUDA GPU run (Google Colab, Tesla T4), separate from this repository's own application code and CPU-based test suite. Full raw execution output: `notebooks/v0.6_real_gpu_checkpoint_resume.ipynb`.

**Why this exists as a separate validation artifact, not folded into the app:** the notebook is a standalone harness that proves the *training-side* mechanics (real LoRA SFT, real checkpoint contents, real process-kill, real resume) work as designed on real hardware. The actual V0.6 application code (`app/training/`, integrated into the existing Worker/fencing/artifact/lineage machinery) is a separate, later implementation step -- this notebook validates the underlying approach before that integration work, and remains as durable evidence this platform's design was checked against a real GPU, not simulated end to end. This machine (the one used for the rest of this project's implementation and testing) has no CUDA GPU -- see REQUIREMENTS_V0.6.md/PROJECT_SCORECARD.md for how the two are kept honestly distinct.

## Stage 1 — real training, checkpoint, hard crash
- Training subprocess ran real CUDA training to step 10, saved `checkpoint-10`.
- Process was hard-killed (exit code 137 -- `SIGKILL`, matching ADR 014's forced-termination model, not a graceful shutdown).
- `checkpoint-10` confirmed to exist on disk *after* process death (proves the checkpoint write itself completed and is durable independent of the process that wrote it).

Note: no `optimizer.pt`/`scheduler.pt`/`rng_state.pth` in the final artifact -- exactly the checkpoint-vs-final-artifact distinction ADR 016/STATE_TRANSITIONS_V0.6.md require structurally: a final model artifact carries what's needed to *use* the model, not what's needed to *resume training* (that's what checkpoints are for).

This is materially stronger evidence than a clean `trainer.train(resume_from_checkpoint=...)` call: the first training process was **actually killed** (`SIGKILL`, exit 137) before completion, not stopped gracefully -- proving the checkpoint/resume path survives a real hard failure, not just an orderly restart.

## What this validates vs. what remains to integrate
This notebook validates the **training-mechanics layer**: real GPU training, real checkpoint contents/durability, real hard-kill survival, real compatibility-gated resume. It does **not** by itself exercise this repository's V0.3 fencing, V0.4 scheduling, or V0.5 artifact/lineage machinery -- that integration (the Worker spawning this as a supervised subprocess, checkpoint registration going through fencing-conditioned writes, artifacts landing in this project's MinIO via the existing upload-lease path) is the implementation work described in `ARCHITECTURE_V0.6.md`/`ADR/014-016`, tracked separately in `PROJECT_SCORECARD.md`.
